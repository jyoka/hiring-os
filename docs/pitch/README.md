## 1. 採用の AI ネイティブ化

**hiring-os 構想資料 / 草案**

企業の bot と求職者の bot が、本人の決めた範囲の中で採用を回す構想です。人は「決める」所にだけ残ります。

PRD 第 2 版(2026-11-18)と調べもの(2026-11 時点)にもとづく草案です。仮説は仮説として、未決は未決として書いています。

ノート: 投資家と事業の相手の方、採用の現場の方の両方に向けた 1 つの資料です。本編のあとに「現場の方に確かめたいこと」と付録(出典)があります。まだ運営者の合意の前の草案で、法の位置も決まっていません。第 2 版で、製品の全体像(6 枚目)を、企業のシステムを作らずにつなぐ形に直しました。連携の戦略(7 から 9 枚目)と収益の形(16 枚目)を足しました。

## 2. 企業は、人が回す仲介に高い対価を払っています

**課題 1**

- **約 9,835 億円**: 人材紹介の手数料(2024 年度)
  - 前年度比 17.6% 増
- **約 103 万円**: 常用就職 1 件あたりの手数料
  - 前年度比 10.9% 増
- **34%**: 週の半分までを、スパムやごみの応募の選別に使う米国の採用担当
  - Greenhouse の調査(2025)

> 注意: 9,835 億円は、医療、介護、保育を含む全職種の手数料です。店舗のアルバイトの負担の根拠としては弱く、現場で確かめます(仮説 H3)。

出典: 厚生労働省 職業紹介事業報告 2024 年度速報([market.md](../research/market.md)、[source-check](../research/source-check.md) #4)/ Greenhouse 2025 年の調査([ai-hiring-tools.md](../research/ai-hiring-tools.md))

ノート: 手数料の数字は全職種で、医療、介護、保育の紹介が大きな部分を占めると見られます(market.md の推測)。最初の対象であるアルバイトの負担は、まだ数字で示せていません。34% は米国の Greenhouse の調査で、原文は「スパムやごみの応募」の選別です。

## 3. 管理しきれない工程と、bot に渡せないデータ

**課題 2**

| 観点 | 調べものでわかったこと |
|---|---|
| 応募と決まる数 | 民営の新規求職申込は約 5,545 万件(42.8% 増)。常用就職は約 92 万件(4.8% 増)にとどまる。申込には重複がある。推測: 選別と連絡の手間が増えた |

| 監査と接続 | API の操作が監査ログに残ると確かめられたのは 2 件だけ。公開 API の文書を確かめられた国内の ATS は HERP Hire だけ |

- 仮説 H3: 一番の負担は連絡と日程調整(特にアルバイト)
- 未確認: どの工程が一番のボトルネックか

## 5. 大手は「自社の囲いの中」で AI ネイティブになっています

**大手の位置と機会**

### 囲いの中: 確かめた事実

**70%**

Indeed の応募のうち、AI の提案や AI のデータにもとづくメールなどから来る割合(会社の発表)

- エージェントは、自社の求人と自社の候補者の中で動く
- 求職者の外部の AI への窓口は求人の検索だけ。応募は自社のサイトに戻す
- 求職者の bot による自動化は、規約で禁じている

### 囲いの外: 確かめた範囲で誰も出していない 4 つ

- 企業の複数のシステムをまたぎ、目的ごとに絞った権限で管理を代わりにやる bot
- 企業が採用流程そのものを、自然言語で設計する仕組み
- 求職に関係するデータだけを見て、ほかを遮断する求職者のアシスタント
- 企業の bot と求職者の bot が直接やり取りする A2A

近いものはあります(Ashby の Custom Agents、Workday Candidate Profile、HERP Career)。違いは「違い」のスライドで扱います。

当初の考え「大手はまだ AI ネイティブでない」は、一部誤りでした。根拠は主に米国の Indeed と LinkedIn です。国内の大手の AI 機能は、一次情報に届いていません。

出典: Recruit Holdings 2026 年 3 月期 Q4 決算説明([job-platforms.md](../research/job-platforms.md)、[source-check](../research/source-check.md) #7)/ [research/README.md](../research/README.md)「結論」

ノート: 70% の内訳は、AI の提案、AI のソーシングと AI の選考のデータにもとづくメールやポップアップです。キーワード検索から来る応募は 30% でした。いずれも会社の発表です。企業の側は、LinkedIn Hiring Pro のように、自社の求人に限ったエージェントを汎用アシスタントの中に出し始めています。

## 6. 企業のシステムは作らず、bot がつなぎに行きます

**製品の全体像**

図(pptx では図形と矢印で描いている):

### 企業がすでに使うシステム(作らない)

- 人事、勤怠、ATS、媒体、メール、予定
  - ↓ 企業の担当者の PC の取り込みゲートへ
  - → サーバーの狭い常時の鍵へ(破線の矢印)

### 企業の担当者の PC

- 取り込みゲート(担当者の権限、目的ごと) ↓
- 企業の bot(流程の定義どおり) ↓
- 企業の承認者(人が決める)

### サーバー(U13 未決、案 C ならここ)

破線の枠で描いている。

- 流程の実行(PC が閉じても動く)
- 狭い常時の鍵(予定の空き、メールの送信)
- 企業の監査の記録
- A2A の取り次ぎ: 企業の bot ↔ A2A の取り次ぎ ↔ 求職者の bot
  - 求職者へ: 求人、結果、面接の枠(受信ゲート)
  - 企業へ: 応募、同意した項目(開示ゲート)

### 求職者のスマホ(ネイティブアプリ)

- メール、予定、通知、共有 ↓
- 取り込みゲート(端末の中で求職の分だけ) ↓
- 求職の金庫 ↓
- 求職者の bot
- 本人(承認と取り消し)

人事、勤怠、ATS、求人媒体は作らず、つなぐ相手にします(D14)。一番の危険は連携です(7 から 9 枚目)。
どの部品をサーバーに置くかは未決です(U13)。案 C では、広く読む鍵で取る元のデータを端末に留め、常に動く部品をサーバーに置きます。
ただし、転送で受けるメール(媒体の応募の通知など)は、サーバーに届きます。

出典: [PRD](../prd.md) 0.1「要約」、4.1「全体の構成」、4.4「bot と記録が動く場所」

ノート: 上の「作らない」の箱は、企業がすでに使うシステムです。hiring-os はそれを作らず、担当者の PC の取り込みゲートからつなぎに行きます。企業の bot は担当者の PC に入り、担当者の権限と企業の承認の上でデータを集めます。求職者の bot はスマホのネイティブアプリです。破線の箱のサーバーは未決です(U13)。PC が閉じていると「1 時間以内に連絡」のような流程が止まるので、案 C では、流程の実行、A2A の取り次ぎ、企業の監査の記録、狭い常時の鍵(予定の空き、メールの送信)をサーバーに置きます。企業の bot と求職者の bot は、このサーバーを通ってつながります。広く読む鍵で取る元のデータは、サーバーに来ません。ただし、転送で受けるメールはサーバーに届き、サーバーのゲートで扱います。PC の bot は、データを取りに行く力を増やすものではなく、元のデータを手元に留めるためのものです(PRD 4.4)。求職者の bot が外に出すものは、すべて開示ゲートを通ります。企業の bot から来るものは受信ゲートを通り、指示ではなくデータとして扱います(D9)。

## 7. 最初は狭い口から、自前でつなぎます

**連携の戦略 1**

| 順 | つなぐ相手 | 口 | 理由 |
|---|---|---|---|
| 1 | 予定の空き | 担当者本人の OAuth(freeBusy、getSchedule) | 9.1 に要る。予定の空きを読む狭い口がある |
| 2 | 応募の受け口 | 媒体の通知メールの転送、CSV、ATS の API | 9.1 に要る。媒体の API は ATS の提携先だけ(U14) |
| 3 | 応募者への連絡 | 店舗のメールの送信(gmail.send) | 9.1 に要る。restricted でなく、セキュリティ評価は要らない |
| 4 | 人事労務 | freee人事労務(OAuth)、SmartHR(トークン) | 欠員の検知に要る。国内ですぐ始められる |
| 5 | ATS | HERP Hire(管理者のキー) | 応募の追加と評価の記入まで API でできる |
| 6 | 勤怠 | KING OF TIME、ジョブカン(申請) | 申請が要る。申請だけ先に出す |
| 7 | チャット | Slack、Teams(通知の投稿だけ) | Slack は外のアプリに厳しい |

国内は自前でつなぎます。統合 API は国内の人事労務と勤怠に届きません(Apideck は SmartHR、freee人事労務などを「まだ対応していない」と明記)。
海外に出る時は統合 API が速いですが、費用は接続ごとです(Merge は月 650 ドルで 10 接続まで)。順は案です(U15)。

出典: [PRD](../prd.md) 4.3 / [integrations-company.md](../research/integrations-company.md)「比べる表」「統合 API の範囲、粗さ、料金の形」/ [source-check](../research/source-check.md) #19 #33

ノート: 連携は一番の危険です。担当者本人の権限(OAuth)で、一番狭い口から始めます。組織全体の権限は初めに求めません。Airシフトとマネーフォワード クラウド給与は公開 API が見つからず、国内の求人媒体も企業が使える公開 API が見つかりませんでした。その相手は次の枚の「API がない時の扱い」に回します。統合 API のスコープは共通モデルの単位で粗いので、項目は取り込みゲートで落とします。

## 8. API がない所は、規約が認める口でつなぎます

**連携の戦略 2**

### API がない時の扱い(D15)

- 1. 規約が認める書き出し: 管理画面の CSV、応募の通知メール
- 2. 本人の操作で渡す: ファイルを置く、共有の口で渡す
- 3. 画面を操作する bot は、規約が自動のアクセスを禁じる相手では使わない
- Indeed の規約は「AI or Agentic AI」での自動のアクセスを禁じる
- SmartHR の規約はスクレイピングを禁じる

### 企業の IT の承認(最大 4 段)

- 1. 端末: 情報システムが PC に配る(Intune など)
- 2. OAuth の同意: 本人の権限なら本人。組織全体の権限は管理者
- 3. チャットのアプリ: ワークスペースの管理者
- 4. 事業者の審査: セキュリティチェックシート(報道)

本人の権限で始め、組織全体の権限を求めません。画面の収録の権限も要らない作りにします(macOS では MDM で配れません)。

- 仮説 H14: 企業は担当者の PC の bot を承認する
- 仮説 H15: 9.1 の連携は手入力なしにつながる

出典: [PRD](../prd.md) 4.3 / [integrations-company.md](../research/integrations-company.md)「規約の問題」「担当者の PC に bot を入れるときの IT の承認」/ [source-check](../research/source-check.md) #20 #21 #25

ノート: 画面を操作する bot は、担当者の権限の全体で動き、scope で絞れません。監査の記録で、担当者本人の操作と区別しにくくもなります。規約を確かめていない相手(バイトル、タウンワークの掲載企業向けなど)でも、確かめるまでは使いません。小さな店舗には情報システム部門がなく、店長か本部が決めると見ています(推測)。店長が PC を持たないこともあります。

## 9. スマホで自動で集められるもの、集められないもの

**連携の戦略 3**

| | iOS | Android |
|---|---|---|
| 自動で集められる | 許可した予定、連絡先、写真、位置。メールは API か IMAP | iOS と同じもの。許可すれば全アプリの通知も |
| 本人の手が要る | 共有の口、ピッカー、Siri から呼ぶ | 共有の口、ピッカー |
| 作れない | ほかのアプリの中身、通知、メール、SMS、画面を読む | 既定でないのに SMS を読む。AccessibilityService で自律で操作する |

### 設計への影響

- 「求職のデータだけ」は OS の許可では絞れない。端末の中のゲートで絞り、ほかは端末の外に出さない
- Gmail の本文を広く読む scope は審査が要る。サーバーに置くなら 12 か月ごとのセキュリティ評価も
- OS のアシスタント(Gemini、Siri)は、第三者のアプリより多くを集められる。差は集める量でなく、遮断と記録と A2A

- 仮説 H17: スマホで足りるデータが集まる
- 未決 U11: メールのつなぎ方

出典: [PRD](../prd.md) 4.3 / [integrations-seeker.md](../research/integrations-seeker.md)「比べる表」「3. アプリストアの審査」「4. メールの API」/ [source-check](../research/source-check.md) #26 から #29

ノート: App Store の 5.1.2(i) は、個人データを第三者の AI を含む第三者に渡す時、渡す先を示して明確な許可を得るよう求めます。Google Play も、本人が予想しない収集の前に、アプリの中での開示と積極的な同意を求めます。Android の版の方が集められるものは多いですが、どちらの OS を先にするかは、利用者の端末の割合(調べていない)と合わせて決めます。求職者の bot が提案に使う求人は、A2A でつながる企業の bot と、本人が共有したものから来ます。大手の求人サイトは読みません。

## 10. 企業の bot: 流程を文で書き、絞った権限で動かす

**企業向け**

### 自然言語で流程を設計する(仮説 H2)

> 記述の例: 「ホールのアルバイト。応募が来たら 1 時間以内に連絡。土日に入れる人を優先して、店長の空きに面接を入れる。採否は店長が決める」

- 起点、条件、手順、承認する人の定義に変え、図と文章で見せる
- 架空の応募者で、サンドボックスで試す
- 違法や差別につながる条件は、設計の段で止める(D11)
- 承認した版だけが本番で動く

### 目的ごとの権限で管理を任せる(仮説 H1)

| 目的 | bot が読むもの |
|---|---|
| 欠員の検知 | 部署、人数、勤怠の集計だけ |
| 面接官の割り当て | 氏名、所属、予定の空きだけ |

初めから人の承認が要る操作: 不採用の通知、内定の送付、給与の提示、データの削除(D3)

bot が読んだもの、したこと、止められたことを、管理者が時系列で見られる

bot は担当者の PC に入り、担当者本人の権限でつなぐ(7、8 枚目)

出典: [PRD](../prd.md) 3.1 体験 1、体験 2、4.3。近い製品: Ashby の Custom Agents、Metaview の管理者の設定([ai-hiring-tools.md](../research/ai-hiring-tools.md)、[ats.md](../research/ats.md))

ノート: 採用流程そのものを自然言語で設計できる製品は、確かめた範囲では見つかりませんでした。年齢の制限は、法が認める例外の事由を利用者が選び、その事由の条件にも合う時だけ通します。D の番号は設計の原則で、運営者の合意で最終の確定になります。Greenhouse MCP も、不採用や採用など 5 つの操作は人が確かめるまで動きません。

## 11. 求職者の bot: 見てよいのは求職に関係するデータだけ

**求職者向け(スマホのアプリ)**

調べた汎用アシスタント 9 件には、データの中身の種類で範囲を決める設定がありませんでした。

| 区分 | 中身 | 決め方 |
|---|---|---|
| A. 金庫に入れる | 職歴、資格、希望条件、応募した求人、企業とのやり取り、面接の予定 | 本人が入れたもの、ゲートを通ったもの |
| B. 外部のうち求職の分 | メールは応募先と求人サービスとのやり取りだけ。予定は空き時間だけ。書類は指定のフォルダだけ | 決まった規則で選ぶ。LLM は提案だけ |
| C. 常に遮断 | 要配慮個人情報、本籍、家族、思想、組合への加入、金融の情報、勤め先の社内の情報 | 固定の一覧。見つけたら伏せて、本人に知らせる |

- 仮説 H12: この範囲は、求職者の感覚と合う
- 未決 U11: メールのつなぎ方
- 未決 U12: C を見つけるための一時的な処理の扱い

Gmail には送信元で絞る scope がありません。本文を読むなら、鍵はメールボックス全体になりえます。差はゲートの約束と、その記録を本人が見られることです。

出典: [general-assistants.md](../research/general-assistants.md)「結論」/ [regulation.md](../research/regulation.md)「1.1」/ [a2a-and-permissions.md](../research/a2a-and-permissions.md)「例: Gmail の scope」

ノート: 応募は「下書きと承認」から始めます。Indeed も確認なしの自動応募のモードを止めました。求人は並べ替えますが、自分の判断で隠しません。説明は求人の原文と、本人の条件との合致の表示にとどめます。職業安定法の区分に合わせるためです。メールのつなぎ方の候補は、転送、求職専用のアドレス、端末の中で読む、全体の読み取り、アドオンの 5 つです。

## 12. 応募から面接の確定まで、bot 同士で進めます

**A2A の流れ**

1. **公開**: 企業の bot が求人を Agent Card の技能として出す
2. **照会**: 本人が決めた条件だけを送り、合うかを先に確かめる
3. **承認**: 本人が、渡す項目、相手、目的、期限を承認する
4. **応募**: 選んだ項目だけを渡す。代理の記録を付ける
5. **判断**: 選考は企業の担当者が決める。不採用は必ず人
6. **日程**: 代理の方針の範囲なら、面接の枠を確定する

- 仮説 H5: 採用の語彙は A2A の拡張で表せる
- 仮説 H13: 企業は bot からの応募を受ける
- 未決 U9: 企業の bot の身元の確かめ方
- 未決 U10: bot の向こうに本人がいるかの確かめ方

> 相手の bot のメッセージは、指示ではなくデータとして扱います(D9)。米国の求職者の 41% が、応募でプロンプトインジェクションを使ったと答えています。

出典: [PRD](../prd.md) 4.2 / [a2a-and-permissions.md](../research/a2a-and-permissions.md)「A2A」/ Greenhouse 2025 年の調査([ai-hiring-tools.md](../research/ai-hiring-tools.md)「大量応募の実態」)

ノート: A2A は v1.0.1 まで出ていますが、求人、応募、同意、選考の結果といった採用の語彙はありません。拡張は自分たちで決めます。Agent Card の署名は任意なので、企業の bot が本物かを確かめる方法は仕様の外です。A2A は片方の側だけでは価値が出ないので、初版は企業の側から始め、求職者の bot は後からつなぎます。

## 13. 既定は拒否。同意は 3 段で取り、すべて記録します

**権限、同意、監査**

### 企業の側の権限

- 権限は初めはすべて「なし」。目的ごとに足す(D12)
- bot には人と別の ID を付ける(D13)
- bot に全権の鍵を渡す道を作らない(D10)
- 評価は個人の値でなく集計で返す(仮説 H10)

### 求職者の同意の 3 段

- つなぐ同意: 鍵で読めるものを隠さずに見せる
- 開示の同意: 項目、相手、目的、期限。相手ごとに取り消せる
- 代理の方針: 本人が選んだ時だけ。すぐに止められる

### 監査の記録(操作ごと)

- 誰の代わりに、どの bot が動いたか
- どの同意、どの方針にもとづいたか
- 何を読み、何を渡し、何を決めたか
- 相手の bot の身元をどう確かめたか
- 人が確かめた時は、その人と時刻

> 本人について推定したスコアを作って、企業に渡しません(D6)。リクナビ DMP フォローの前例から決めた原則です。

D の番号は設計の原則です。運営者の合意で最終の確定になります。記録の保存期間は未決です(U5)。

出典: [PRD](../prd.md) 5 節 / [stripe-modular-agentic.md](../research/stripe-modular-agentic.md) / [a2a-and-permissions.md](../research/a2a-and-permissions.md)「6」/ [risks.md](../research/risks.md)、[source-check](../research/source-check.md) #16 #18

ノート: 開示の同意は RFC 9396 の authorization_details の形で、代理の方針は AP2 の mandate と同じ形で持つ想定です(仮説 H11)。既定は「毎回、本人が承認」で、代理の方針では開示の同意の外に開示を広げられません。保存期間は、カリフォルニア州の規則が雇用の記録を 4 年以上残すとしており、データの最小化とぶつかります。

## 14. 既存の製品と何が違うか

**違い**

| 比べる相手 | すでにできること | hiring-os の差 |
|---|---|---|
| 汎用アシスタント(調べた 9 件) | アプリ、ツール、サイトの単位で権限を渡す。記憶は会話の全体から作る | 求職に関係するデータの種類で範囲を決める。記憶は金庫の中だけ |
| 大手(Indeed、LinkedIn) | 自社の求人と候補者の中で、エージェントが動く | 大手の外側に座り、企業と求職者の bot を A2A でつなぐ |
| ディップの面接コボット、Paradox | 応募者への自動の連絡と日程調整 | 店長が文で書いた自社の流程どおりに動く。日程の口を A2A の技能で持つ |
| Workday Candidate Profile、HERP Career | 求職者が情報を持つ。前者は見せる相手を求職者が決める(発表のみ) | ATS をまたぐ。外部のソースを求職の分だけに絞り、渡した記録を相手ごとに見せる |

正直な弱み: メールを全体の読み取りでつなぐと、鍵の広さは汎用アシスタントと同じです(U11)。推測: Candidate Profile が一般提供されると、Workday を使う大企業では価値の一部が重なります。

出典: [general-assistants.md](../research/general-assistants.md) / [job-platforms.md](../research/job-platforms.md) / [ai-hiring-tools.md](../research/ai-hiring-tools.md) / [ats.md](../research/ats.md)「Workday Recruiting」「競合の見え方」/ [PRD](../prd.md) 5.3、6

ノート: 求職者の bot は単独のスマホのアプリとして入れてもらいます。汎用アシスタントの中の口(MCP)は、アプリに来てもらう入口として補います(仮説 H7、第 2 版で直した)。OS のアシスタント(Gemini、Siri)は、第三者のアプリより多くを集められます。差は集める量ではなく、遮断と記録と A2A です。国内では LINEヤフーの Agent i が領域ごとのエージェントを増やしており、仕事探しの領域が足されると強い相手になると見ています(推測)。Workday Candidate Profile の一般提供は 2027 年初めの予定です。

## 15. 法の位置は、まだ決まっていません

**法の位置**

適法かどうかは確かめていません。労働局と弁護士に確かめてから、事業の区分を決めます。

| 条件 | 中身 | いまの設計での扱い |
|---|---|---|
| 職業安定法 | AI の自動処理でも、事業者の判断で選別、加工、連絡の差配をすれば職業紹介(許可が必要) | 判断は企業と本人に戻す。求人を隠さず、文言も書き換えない |
| 求職者からの課金 | 特定募集情報等提供と有料職業紹介の事業者は、原則として求職者から報酬を取れない | 収益の形は未決(U4)。16 枚目で比べる |
| 個人情報保護法 | 第三者提供と要配慮個人情報の取得は、原則として本人の同意が要る。改正法で課徴金が入る | 開示の同意で取る。一時的な処理の扱いは未決(U12) |
| EU AI 法、米国の訴訟 | 採用の AI は高リスク。Mobley v. Workday でベンダーの責任が争われている | 重い操作は人が承認(D3)。海外に出るかは未決(U7) |

- 未決 U1: 道具の提供 / 特定募集情報等提供の届出 / 職業紹介の許可

出典: [regulation.md](../research/regulation.md)「1.1」「1.2」「1.3」「2.1」/ [risks.md](../research/risks.md)「2. 訴訟」/ 厚生労働省のページ([source-check](../research/source-check.md) #1)

ノート: 「企業が決めた基準を記録に残し、そのとおりに実行する」形は、職業紹介に当たらないための根拠にもなると見ていますが、推測です。両方の bot を同じ事業者が動かすと「あっせん」に一番近くなる、というのも推測です。どの段で「合う、合わない」を決めるかで、日本では職業紹介、EU では GDPR 第 22 条に近づきます。大手の規約も、求職者の bot による応募の自動化とぶつかります。

## 17. 店長が文で書いた流程どおりに、bot が応募者への連絡と面接の日程調整をします

**最初に確かめる体験(PRD 9.1): 小さな店舗のアルバイト採用**

### 範囲

- 企業の側だけ。応募は既存の媒体と ATS から受ける
- 読むのは店長の予定の空きだけ。人事のデータは読まない
- 採否の連絡は、店長が承認して送る

### 確かめること

- 店長が書いた流程が、意図どおりに動くか(H2)
- 店長の作業時間と取りこぼしが減るか(H3)
- 要る連携が、規約の中で手入力なしにつながるか(H15)

### この体験の限り

- 応募の受け口が成り立つかは未決(U14)
- 自動の連絡と日程調整は、面接コボットなどがすでに出している。残る差は H2 だけ
- 職業紹介に当たりにくいのは推測(U1)

出典: [PRD](../prd.md) 9.1 / [integrations-company.md](../research/integrations-company.md)「求人媒体の管理画面」/ [job-platforms.md](../research/job-platforms.md)「ディップ(バイトル)」/ [ai-hiring-tools.md](../research/ai-hiring-tools.md)「Paradox」

ノート: 選んだ理由は、H3 と H2 を同時に確かめられること、要る連携が予定の空き、応募の受け口、連絡の 3 つで少ないこと、採否は店長が決めるので職業紹介に当たりにくいこと(推測)です。最初の対象をアルバイトにするのは仮の値(U2)です。応募の受け口の候補は、媒体の通知メールの転送、管理画面の CSV、ATS の API です。媒体の API は ATS の提携先にしか開いていません。日程の口を A2A の技能として作るのは形だけです(H5)。H1、H4、H5、H8、H17 はここでは確かめません。H14(担当者の PC の bot の承認)も、ここでは確かめません。9.1 に要る連携は案 C ではどれもサーバーで動き、PC の bot はほぼ働かないからです。H14 は C2 と C5 で確かめます。LinkedIn Hiring Pro が同じ中小企業に求人の掲載を出している点にも注意が要ります。

## 23. 問い 3: 求職者の bot からの応募を受けますか

**企業の採用担当の方へ**

### 見本 A

**証拠と上限が付いた応募**

- hiring-os が本人を確かめた印
- 本人が承認した証拠
- 応募の数の上限

### 見本 B

**何も付かない応募**

- 本人がいるかは分からない
- 承認の証拠はない
- 数の上限はない

A と B のそれぞれを受けますか。受けないなら、何が付けば受けますか。

私たちの仮説: 本人の確認、数の上限、承認の証拠が付くなら、企業は bot からの応募を受けます(H13)。採用側は AI を使った大量応募を、なりすましとして止めはじめています。

出典: [PRD](../prd.md) 4.2、7.2 H13 / [ai-hiring-tools.md](../research/ai-hiring-tools.md)「採用側の対策」(Greenhouse)

ノート: 企業が求職者の bot からの応募を受ける理由は、まだありません。この問いの答えで、求職者の bot の確かめ方(U10)を決めます。

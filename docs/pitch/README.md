## 1. 採用の AI ネイティブ化

**hiring-os 構想資料 / 草案**

企業の bot と求職者の bot が、本人の決めた範囲の中で採用を回す構想です。人は「決める」所にだけ残ります。

PRD 初版(2026-11-11)と調べもの(2026-11 時点)にもとづく草案です。仮説は仮説として、未決は未決として書いています。

ノート: 投資家と事業の相手の方、採用の現場の方の両方に向けた 1 つの資料です。本編のあとに「現場の方に確かめたいこと」と付録(出典)があります。まだ運営者の合意の前の草案で、法の位置も決まっていません。

## 2. 企業は、人が回す仲介に高い対価を払っています

**課題 1**

- **約 9,835 億円**: 人材紹介の手数料(2024 年度)
  - 前年度比 17.6% 増
- **約 103 万円**: 常用就職 1 件あたりの手数料
  - 前年度比 10.9% 増
- **34%**: 週の半分までを、スパムやごみの応募の選別に使う米国の採用担当
  - Greenhouse の調査(2025)

> 注意: 9,835 億円は、医療、介護、保育を含む全職種の手数料です。店舗のアルバイトの負担の根拠としては弱く、現場で確かめます(仮説 H3)。

出典: 厚生労働省 職業紹介事業報告 2024 年度速報([market.md](../research/market.md)、[source-check](../research/source-check.md) #4)/ Greenhouse 2025 年の調査([ai-hiring-tools.md](../research/ai-hiring-tools.md))

ノート: 手数料の数字は全職種で、医療、介護、保育の紹介が大きな部分を占めると見られます(market.md の推測)。最初の対象であるアルバイトの負担は、まだ数字で示せていません。34% は米国の Greenhouse の調査で、原文は「スパムやごみの応募」の選別です。

## 3. 管理しきれない工程と、bot に渡せないデータ

**課題 2**

| 観点 | 調べものでわかったこと |
|---|---|
| 応募と決まる数 | 民営の新規求職申込は約 5,545 万件(42.8% 増)。常用就職は約 92 万件(4.8% 増)にとどまる。申込には重複がある。推測: 選別と連絡の手間が増えた |
| 流程の後半 | Indeed の CEO は、内定、条件交渉、入社手続きの自動化を後回しにした(決算説明) |
| 人事のデータ | API はあるが、スコープは粗い。項目や対象者で絞れるのは HiBob、SmartHR、Rippling など一部 |
| 監査と接続 | API の操作が監査ログに残ると確かめられたのは 2 件だけ。公開 API の文書を確かめられた国内の ATS は HERP Hire だけ |

- 仮説 H3: 一番の負担は連絡と日程調整(特にアルバイト)
- 未確認: どの工程が一番のボトルネックか

出典: 厚生労働省 職業紹介事業報告 2024 年度速報([market.md](../research/market.md)「2」)/ [job-platforms.md](../research/job-platforms.md)「経営の方針」/ [hr-data.md](../research/hr-data.md)、[ats.md](../research/ats.md)「結論」

ノート: 監査ログの 2 件は SAP SuccessFactors と Merge Agent Handler です。SAP SuccessFactors には、読み取り専用の権限がロールの権限を飛ばす抜け道もあります。国内の中小企業の多くは、bot から API で触れない道具で採用を回していると見込んでいますが、これは推測です。

## 5. 大手は「自社の囲いの中」で AI ネイティブになっています

**大手の位置と機会**

### 囲いの中: 確かめた事実

**70%**

Indeed の応募のうち、AI の提案や AI のデータにもとづくメールなどから来る割合(会社の発表)

- エージェントは、自社の求人と自社の候補者の中で動く
- 求職者の外部の AI への窓口は求人の検索だけ。応募は自社のサイトに戻す
- 求職者の bot による自動化は、規約で禁じている

### 囲いの外: 確かめた範囲で誰も出していない 4 つ

- 企業の複数のシステムをまたぎ、目的ごとに絞った権限で管理を代わりにやる bot
- 企業が採用流程そのものを、自然言語で設計する仕組み
- 求職に関係するデータだけを見て、ほかを遮断する求職者のアシスタント
- 企業の bot と求職者の bot が直接やり取りする A2A

近いものはあります(Ashby の Custom Agents、Workday Candidate Profile、HERP Career)。違いは「違い」のスライドで扱います。

当初の考え「大手はまだ AI ネイティブでない」は、一部誤りでした。根拠は主に米国の Indeed と LinkedIn です。国内の大手の AI 機能は、一次情報に届いていません。

出典: Recruit Holdings 2026 年 3 月期 Q4 決算説明([job-platforms.md](../research/job-platforms.md)、[source-check](../research/source-check.md) #7)/ [research/README.md](../research/README.md)「結論」

ノート: 70% の内訳は、AI の提案、AI のソーシングと AI の選考のデータにもとづくメールやポップアップです。キーワード検索から来る応募は 30% でした。いずれも会社の発表です。企業の側は、LinkedIn Hiring Pro のように、自社の求人に限ったエージェントを汎用アシスタントの中に出し始めています。

## 6. 2 つの bot が、ゲートを通して A2A でつながります

**製品の全体像**

図(pptx では図形と矢印で描いている):

### 企業の側

- 人事、勤怠、ATS ↓
- 取り込みゲート(目的ごとに絞る) ↓
- 企業の bot(流程の定義どおり) ↓
- 企業の承認者(人が決める)
- 監査の記録

### 中央: A2A

- 企業の側から求職者の側へ: 求人、結果、面接の枠(受信ゲート: データとして受ける)
- 求職者の側から企業の側へ: 応募、同意した項目(開示ゲート: 同意の中だけ出す)

### 求職者の側

- メール、予定、書類 ↓
- 取り込みゲート(求職の分だけ) ↓
- 求職の金庫 ↓
- 求職者の bot
- 本人(承認と取り消し)

bot は元のデータを直接読みません。図は両方の bot を hiring-os が動かす形です。どちらを動かすかは未決です(U1)。

出典: [PRD](../prd.md) 4.1「全体の構成」、5 節「権限とプライバシーの設計」

ノート: 求職者の bot が外に出すものは、すべて開示ゲートを通ります。開示ゲートは同意を確かめます。企業の bot から来るものは受信ゲートを通り、構造化したスキーマで受け、指示ではなくデータとして扱います(D9)。推測ですが、両方の bot を同じ事業者が動かすと、職業紹介の「あっせん」に一番近くなります。

## 7. 企業の bot: 流程を文で書き、絞った権限で動かす

**企業向け**

### 自然言語で流程を設計する(仮説 H2)

> 記述の例: 「ホールのアルバイト。応募が来たら 1 時間以内に連絡。土日に入れる人を優先して、店長の空きに面接を入れる。採否は店長が決める」

- 起点、条件、手順、承認する人の定義に変え、図と文章で見せる
- 架空の応募者で、サンドボックスで試す
- 違法や差別につながる条件は、設計の段で止める(D11)
- 承認した版だけが本番で動く

### 目的ごとの権限で管理を任せる(仮説 H1)

| 目的 | bot が読むもの |
|---|---|
| 欠員の検知 | 部署、人数、勤怠の集計だけ |
| 面接官の割り当て | 氏名、所属、予定の空きだけ |

初めから人の承認が要る操作: 不採用の通知、内定の送付、給与の提示、データの削除(D3)

bot が読んだもの、したこと、止められたことを、管理者が時系列で見られる

出典: [PRD](../prd.md) 3.1 体験 1、体験 2。近い製品: Ashby の Custom Agents、Metaview の管理者の設定([ai-hiring-tools.md](../research/ai-hiring-tools.md)、[ats.md](../research/ats.md))

ノート: 採用流程そのものを自然言語で設計できる製品は、確かめた範囲では見つかりませんでした。年齢の制限は、法が認める例外の事由を利用者が選び、その事由の条件にも合う時だけ通します。D の番号は設計の原則で、運営者の合意で最終の確定になります。Greenhouse MCP も、不採用や採用など 5 つの操作は人が確かめるまで動きません。

## 8. 求職者の bot: 見てよいのは求職に関係するデータだけ

**求職者向け**

調べた汎用アシスタント 9 件には、データの中身の種類で範囲を決める設定がありませんでした。

| 区分 | 中身 | 決め方 |
|---|---|---|
| A. 金庫に入れる | 職歴、資格、希望条件、応募した求人、企業とのやり取り、面接の予定 | 本人が入れたもの、ゲートを通ったもの |
| B. 外部のうち求職の分 | メールは応募先と求人サービスとのやり取りだけ。予定は空き時間だけ。書類は指定のフォルダだけ | 決まった規則で選ぶ。LLM は提案だけ |
| C. 常に遮断 | 要配慮個人情報、本籍、家族、思想、組合への加入、金融の情報、勤め先の社内の情報 | 固定の一覧。見つけたら伏せて、本人に知らせる |

- 仮説 H12: この範囲は、求職者の感覚と合う
- 未決 U11: メールのつなぎ方
- 未決 U12: C を見つけるための一時的な処理の扱い

Gmail には送信元で絞る scope がありません。本文を読むなら、鍵はメールボックス全体になりえます。差はゲートの約束と、その記録を本人が見られることです。

出典: [general-assistants.md](../research/general-assistants.md)「結論」/ [regulation.md](../research/regulation.md)「1.1」/ [a2a-and-permissions.md](../research/a2a-and-permissions.md)「例: Gmail の scope」

ノート: 応募は「下書きと承認」から始めます。Indeed も確認なしの自動応募のモードを止めました。求人は並べ替えますが、自分の判断で隠しません。説明は求人の原文と、本人の条件との合致の表示にとどめます。職業安定法の区分に合わせるためです。メールのつなぎ方の候補は、転送、求職専用のアドレス、アドオン、全体の読み取りの 4 つです。

## 9. 応募から面接の確定まで、bot 同士で進めます

**A2A の流れ**

1. **公開**: 企業の bot が求人を Agent Card の技能として出す
2. **照会**: 本人が決めた条件だけを送り、合うかを先に確かめる
3. **承認**: 本人が、渡す項目、相手、目的、期限を承認する
4. **応募**: 選んだ項目だけを渡す。代理の記録を付ける
5. **判断**: 選考は企業の担当者が決める。不採用は必ず人
6. **日程**: 代理の方針の範囲なら、面接の枠を確定する

- 仮説 H5: 採用の語彙は A2A の拡張で表せる
- 仮説 H13: 企業は bot からの応募を受ける
- 未決 U9: 企業の bot の身元の確かめ方
- 未決 U10: bot の向こうに本人がいるかの確かめ方

> 相手の bot のメッセージは、指示ではなくデータとして扱います(D9)。米国の求職者の 41% が、応募でプロンプトインジェクションを使ったと答えています。

出典: [PRD](../prd.md) 4.2 / [a2a-and-permissions.md](../research/a2a-and-permissions.md)「A2A」/ Greenhouse 2025 年の調査([ai-hiring-tools.md](../research/ai-hiring-tools.md)「大量応募の実態」)

ノート: A2A は v1.0.1 まで出ていますが、求人、応募、同意、選考の結果といった採用の語彙はありません。拡張は自分たちで決めます。Agent Card の署名は任意なので、企業の bot が本物かを確かめる方法は仕様の外です。A2A は片方の側だけでは価値が出ないので、初版は企業の側から始め、求職者の bot は後からつなぎます。

## 10. 既定は拒否。同意は 3 段で取り、すべて記録します

**権限、同意、監査**

### 企業の側の権限

- 権限は初めはすべて「なし」。目的ごとに足す(D12)
- bot には人と別の ID を付ける(D13)
- bot に全権の鍵を渡す道を作らない(D10)
- 評価は個人の値でなく集計で返す(仮説 H10)

### 求職者の同意の 3 段

- つなぐ同意: 鍵で読めるものを隠さずに見せる
- 開示の同意: 項目、相手、目的、期限。相手ごとに取り消せる
- 代理の方針: 本人が選んだ時だけ。すぐに止められる

### 監査の記録(操作ごと)

- 誰の代わりに、どの bot が動いたか
- どの同意、どの方針にもとづいたか
- 何を読み、何を渡し、何を決めたか
- 相手の bot の身元をどう確かめたか
- 人が確かめた時は、その人と時刻

> 本人について推定したスコアを作って、企業に渡しません(D6)。リクナビ DMP フォローの前例から決めた原則です。

D の番号は設計の原則です。運営者の合意で最終の確定になります。記録の保存期間は未決です(U5)。

出典: [PRD](../prd.md) 5 節 / [stripe-modular-agentic.md](../research/stripe-modular-agentic.md) / [a2a-and-permissions.md](../research/a2a-and-permissions.md)「6」/ [risks.md](../research/risks.md)、[source-check](../research/source-check.md) #16 #18

ノート: 開示の同意は RFC 9396 の authorization_details の形で、代理の方針は AP2 の mandate と同じ形で持つ想定です(仮説 H11)。既定は「毎回、本人が承認」で、代理の方針では開示の同意の外に開示を広げられません。保存期間は、カリフォルニア州の規則が雇用の記録を 4 年以上残すとしており、データの最小化とぶつかります。

## 11. 既存の製品と何が違うか

**違い**

| 比べる相手 | すでにできること | hiring-os の差 |
|---|---|---|
| 汎用アシスタント(調べた 9 件) | アプリ、ツール、サイトの単位で権限を渡す。記憶は会話の全体から作る | 求職に関係するデータの種類で範囲を決める。記憶は金庫の中だけ |
| 大手(Indeed、LinkedIn) | 自社の求人と候補者の中で、エージェントが動く | 大手の外側に座り、企業と求職者の bot を A2A でつなぐ |
| ディップの面接コボット、Paradox | 応募者への自動の連絡と日程調整 | 店長が文で書いた自社の流程どおりに動く。日程の口を A2A の技能で持つ |
| Workday Candidate Profile、HERP Career | 求職者が情報を持つ。前者は見せる相手を求職者が決める(発表のみ) | ATS をまたぐ。外部のソースを求職の分だけに絞り、渡した記録を相手ごとに見せる |

正直な弱み: メールを全体の読み取りでつなぐと、鍵の広さは汎用アシスタントと同じです(U11)。推測: Candidate Profile が一般提供されると、Workday を使う大企業では価値の一部が重なります。

出典: [general-assistants.md](../research/general-assistants.md) / [job-platforms.md](../research/job-platforms.md) / [ai-hiring-tools.md](../research/ai-hiring-tools.md) / [ats.md](../research/ats.md)「Workday Recruiting」「競合の見え方」/ [PRD](../prd.md) 5.3、6

ノート: 汎用アシスタントと戦うより、その中にも出る考えです(仮説 H7)。hiring-os の MCP サーバーを「求職に関係するデータだけを返す口」として出します。国内では LINEヤフーの Agent i が領域ごとのエージェントを増やしており、仕事探しの領域が足されると強い相手になると見ています(推測)。Workday Candidate Profile の一般提供は 2027 年初めの予定です。

## 12. 法の位置は、まだ決まっていません

**法の位置**

適法かどうかは確かめていません。労働局と弁護士に確かめてから、事業の区分を決めます。

| 条件 | 中身 | いまの設計での扱い |
|---|---|---|
| 職業安定法 | AI の自動処理でも、事業者の判断で選別、加工、連絡の差配をすれば職業紹介(許可が必要) | 判断は企業と本人に戻す。求人を隠さず、文言も書き換えない |
| 求職者からの課金 | 特定募集情報等提供と有料職業紹介の事業者は、原則として求職者から報酬を取れない | 収益の形は未決(U4) |
| 個人情報保護法 | 第三者提供と要配慮個人情報の取得は、原則として本人の同意が要る。改正法で課徴金が入る | 開示の同意で取る。一時的な処理の扱いは未決(U12) |
| EU AI 法、米国の訴訟 | 採用の AI は高リスク。Mobley v. Workday でベンダーの責任が争われている | 重い操作は人が承認(D3)。海外に出るかは未決(U7) |

- 未決 U1: 道具の提供 / 特定募集情報等提供の届出 / 職業紹介の許可

出典: [regulation.md](../research/regulation.md)「1.1」「1.2」「1.3」「2.1」/ [risks.md](../research/risks.md)「2. 訴訟」/ 厚生労働省のページ([source-check](../research/source-check.md) #1)

ノート: 「企業が決めた基準を記録に残し、そのとおりに実行する」形は、職業紹介に当たらないための根拠にもなると見ていますが、推測です。両方の bot を同じ事業者が動かすと「あっせん」に一番近くなる、というのも推測です。どの段で「合う、合わない」を決めるかで、日本では職業紹介、EU では GDPR 第 22 条に近づきます。大手の規約も、求職者の bot による応募の自動化とぶつかります。

## 13. 店長が文で書いた流程どおりに、bot が応募者への連絡と面接の日程調整をします

**最初に確かめる体験(PRD 9.1): 小さな店舗のアルバイト採用**

### 範囲

- 企業の側だけ。応募者は Web のリンクで日程を選ぶ
- 人事のデータは読まない。読むのは店長の予定の空きだけ
- 採否の連絡は、店長が承認して送る

### 確かめること

- 店長が書いた流程が、意図どおりに動くか(H2)
- 店長の作業時間と取りこぼしが減るか(H3)
- 日程の口を A2A の技能として作る(H5 は形だけ)

### この体験の限り

- 自動の連絡と日程調整は、面接コボットや Paradox がすでに出している
- 残る差は H2 だけ。H1、H4、H5、H8 はここでは確かめない
- 職業紹介に当たりにくいのは推測。U1 の確認が要る

出典: [PRD](../prd.md) 9.1 / [job-platforms.md](../research/job-platforms.md)「ディップ(バイトル)」/ [ai-hiring-tools.md](../research/ai-hiring-tools.md)「Paradox」

ノート: 選んだ理由は、H3 と H2 を同時に確かめられること、面接の日程は A2A にしやすい部品で後から求職者の bot をつなげること、採否は店長が決めるので職業紹介に当たりにくいこと(推測)です。最初の対象をアルバイトにするのは仮の値(U2)です。応募をどこから受けるかは U3 と C5 で決めます。LinkedIn Hiring Pro が同じ中小企業に求人の掲載を出している点にも注意が要ります。
